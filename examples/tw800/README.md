# Example: a complete assessment of a fictional product

This folder is one complete assessment export, put here so that you can read it, diff it and feed it to your own tooling
before you give anyone your e-mail address. The product is fictional: Substation Cellular Router (TW800 Series), assessed by a fictional organisation.
It is a **completed and approved** assessment, exported by the product's own export (archive layout 5, engine 0.5.3).

## Who it is for, and what it claims

For an engineer or compliance lead who wants to test the claim that an assessment is computed, traceable and open to checking:
why this risk level, and which fact about the product produced it. It shows 61 answers, 31
assignments of measures, 160 computed risks and 121 recorded treatment rows.

It does **not** claim that the product is certified, that it conforms to a regulation or a standard, that its catalogue is
validated, or that the scores are calibrated. It shows what the method computes from stated inputs, and nothing more.

## Layout

`archive/` is the assessment archive exactly as the product writes it, byte for byte; nothing in it was edited, so its own
`manifest.json` still verifies every file. Beside it: this README, `VERSIONS.json` (what it was produced against) and `LICENSE`.

| Path | What it is |
|---|---|
| `archive/input/answers.yaml`, `mitigations.yaml`, `treatments.yaml`, `qi-acceptances.yaml`, `condition-handovers.yaml`, `toe.yaml` | What the assessors entered, in plain YAML keyed by the codes the questionnaire shows |
| `archive/input/model.json`, `catalogs/*.json`, `frameworks.json` | The model and catalogue snapshots this assessment is pinned to |
| `archive/input/tracing.yaml` | No confirmations are recorded in this example, so there is no confirmed-only comparison to read. Where it holds anything it is only a count, on purpose: the confirmed path ids are generated by the engine and live in `archive/output/engine-result.json`, under `tracing` (empty when nothing is confirmed) |
| `archive/output/engine-result.json` | **The machine-readable result**: the computed risks, treatments, quality indicators and report tables, in the `json-export` format of the published schemas. Start here |
| `archive/output/reports/*.pdf`, `archive/output/traceability.xlsx` | **Derived views** of that result, rendered for people. They are not data; see "Regenerating" |
| `archive/provenance.json` | The only file with internal identifiers, here those of the fictional seeded organisation, and `localKeys`, the map from the local keys used elsewhere to those identifiers |
| `archive/manifest.json` | A SHA-256 for every file, the engine version, the input hash and the pinned versions; written last |
| `archive/LICENSE-CATALOG.md` | The licence and attribution of the catalogue content |
| `archive/regenerate.mjs` | Verifies the manifest with Node alone (see below) |

Everywhere else a row is named by a local key that means something inside this archive only: `asset-1` and `interface-1`
in `input/toe.yaml`, `organisation` in `input/model.json`, and `revision-1` in `output/engine-result.json`.
`localKeys` in `archive/provenance.json` says which identifier each stands for; delete that file and nothing else changes.
The PDFs print no identifier either (`pdfsWithDatabaseId` in that file is empty here); the example's checks read their text.

## One trace: from an answer to a risk to its treatment

Risk **R9-40** of this example. Each line says where it is read from.

- The path, from `archive/output/engine-result.json` (`risks.initial`): AS9 then AS40; its final step is AS40.
  - AS9, Attacking the product's internal gateway from the Internet (needs QA2[Yes|Internet-facing gateway]; answers given: QI15: Yes / Major disturbance; measures assigned: CM1)
  - AS40, Abusing the lack of a software update functionality to exploit an unpatched vulnerability (needs no particular answer; answers given: QI1: Yes / No; QI10: Yes / Potentially dangerous situation; QI11: Yes / Personal data (significant); QI12: Yes / IP (slightly innovative); QI13: Yes / Major disturbance; QI14: Yes / Major disturbance; QI15: Yes / Major disturbance; QI16: No; measures assigned: A46, A47)
- Initial risk, same file: attack potential sum 13 (class Enhanced-Basic), damage level High, so the risk is **Very High**.
- With the assigned measures (`risks.residual`, from `archive/input/mitigations.yaml`): sum 23 (class High), risk **High**, relying on CM1.
- The recorded treatment, `archive/input/treatments.yaml`: **mitigate**, with the rationale "Mitigate the IP-network exposure path to unpatched-vulnerability exploitation; no agreed third-party risk transfer is claimed. Retain planned device firewall. D...".
- Tracing: No confirmations are recorded in this example, so there is no confirmed-only comparison to read.

A measure assigned in the catalogue is credited, not verified, and planned controls are marked as such where they occur. The
result states what it relies on; it does not claim that a measure works.

## Checking it

1. **Hashes.** `node archive/regenerate.mjs` (Node 24, no installation, no network, read-only) recomputes every file's SHA-256
   against `archive/manifest.json`. If they match, the files agree with the manifest; the manifest is not signed, so compare
   its SHA-256 (the script prints it) with one you received separately, or give it as `--expect-manifest-sha256 <hash>`. Any
   other SHA-256 tool does the same job from the manifest's list.
2. **Schemas.** Each machine-readable file follows a published schema at https://data.atrekos.com/schemas/ (the manifest, the
   provenance file, the result as `json-export` and the inputs as `archive-input`, each at the version the file names). Any
   JSON Schema 2020-12 validator checks them.
3. **Reproducibility.** The initial and residual risks in `output/engine-result.json` are the engine's result for the files in
   `input/`, and the product's own repository checks this on every change. A reader with the engine can recompute them. The
   rest of that file (quality indicators, report tables, tracing) cannot be recomputed from `input/` alone, because the
   archive leaves out the identifiers the application generates, such as those of custom mitigations; the archive's hashes
   still cover it.

## Regenerating the PDFs and the workbook

The reports are rendered from the result by the application, which prints its report pages with headless Chromium. To rebuild
them you need the application, a database seeded with this example and Chromium; the commands, from a checkout of the
application, are in `docs/runbooks/example-export.md`: seed the example (`scripts/seed-example.ts` with its fixture), start the
application, then run `scripts/generate-example-export.ts`. The result is this folder again, except that the identifiers the
database generates, the times, and the rendered files differ.
